# Bank / UPI credit-alert templates and Android capture constraints

Companion to `bank-sms-corpus.json` (45 entries: 27 credits across 21 institutions/apps, 18 negatives; 8 verbatim-verified). Written 2026-09-06 for the `BankSmsParser` / `SmsReceiverSource` / `NotificationListenerSource` authors (SPEC §1 Mode 1, §4). Everything marked **[emu-verified]** was run today on this machine: emulator 36.3.10, adb 36.0.2, AVD `Medium_Phone_API_36.1`, image `google/sdk_gphone64_x86_64/emu64xa:16/BE4B.251210.005` (API 36, Google Play).

Honesty note on the corpus: public sources rarely quote whole bank SMS. Entries marked `verified` are copied from a public page/repo; `reconstructed` entries follow each bank's known phrasing but the exact wording is my best reconstruction. Before the event, capture real ones on the iQOO loaner with `adb shell content query --uri content://sms/inbox --projection address:body` and `adb shell dumpsys notification --noredact` and replace the reconstructed rows.

## 1. Per-institution template patterns

Sender IDs: DLT header = 2-char operator/circle prefix + `-` + 6-char registered header; since 6 May 2025 TRAI appends `-S` (service), `-T` (transactional/OTP), `-P` (promo), `-G` (govt) ([TRAI suffix rule](https://kb.smsalert.co.in/knowledgebase/trai-mandates-header-suffixes-for-sms-new-rules-effective-from-may-6-2025/)). Real observed headers: `AD-SBIINB-S`, `VM-SBICRD-T`, `VM/BX/QP/JK/JD-SBIUPI`, `CP/VM/AD/JM/AX-HDFCBK-S`, `AD-ICICIT-S`, `AD-ICICIO-T`, `JD-AxisBK-S`, `AD/AX/CP/VM-AXISBK-S`, `VM-KOTAKB-T`, `AX-PNBSMS-S`, `TM-INDUSB-S`, `JM-AUBANK-S`, `AX-IDFCFB-S`, `VK-BHIMAP-S` ([TechnoFino -S thread](https://technofino.in/community/threads/bank-cc-official-sms-ending-with-s.40715/), [payload.txt](https://github.com/nileshnishad/apiservice/blob/main/payload.txt)). Header list per bank: [abhishekjnvk gist](https://gist.github.com/abhishekjnvk/ad596df86a22291ccd76cf29af52b656), [Moneyprism banks.dart](https://github.com/qtw4c7phzx-alt/Moneyprism/blob/main/lib/core/parser/india/constants/banks.dart). ## 2. Regex recommendations and check ordering

All patterns case-insensitive; run on `body` for SMS and on `title + "\n" + bigText ?: text` for notifications. Money is parsed to `Long` paise from the string (`"1,50,000.00"` → strip commas → split on `.` → `rupees*100 + paise`), never via `Double`.

```
AMOUNT   (?:rs\.?|inr|₹)\s*:?\s*((?:\d{1,3}(?:,\d{2,3})+|\d+)(?:\.\d{1,2})?)
           – accepts Rs8700, Rs.500.00, INR 1,50,000.00, ₹1,250.50. Validate captured
             group with ^\d+(\.\d{1,2})?$ after removing commas.
           – Ignore an amount whose preceding 20 chars contain bal|balance|limit|lmt|avl|avail|total
             (Axis/BoB/PNB put the balance after the credit amount; promos put lakh figures before "credited").
           – If more than one candidate survives, take the one closest to the credit keyword.

UTR      (?:upi\s*ref(?:\s*no)?\.?|ref(?:\s*no)?\.?|rrn|utr|txn\s*id|upi)\s*[:\-#]?\s*\(?\s*(\d{12})\b
         | upi/(?:cr|dr|p2a|p2m)?/?(\d{12})           – BoB/Union/Axis slash format
         | upi:(\d{12})                                  – ICICI/PNB glued format
         – Fallback: any standalone \b\d{12}\b not immediately after a/c|acct|account|card|x+.
         – Normalise to digits only (SPEC §4). Accept 10–12 digits as "partial" only from the fallback path;
           scams commonly have 11 digits (see corpus scam-hdfc-lookalike-10digit).

PAYER    from\s+(?:vpa\s+)?([a-z0-9._-]+@[a-z]{2,})                  – VPA first (most precise)
         | (?:from|transfer from|by transfer from)\s+([a-z][a-z .&'-]{1,40}?)(?=\s*[.,;(]|\s+on\b|\s+upi|\s+ref|\s*$)
         | upi/(?:cr|p2a|p2m)/\d{12}/([a-z][a-z .]+?)(?=/|\.|\s|$)     – slash format name
         | ^(.+?)\s+paid you\s+₹                                        – GPay title
         | received\s+₹?\s*[\d,.]+\s+from\s+(.+)$                       – PhonePe title
         – Trim, collapse spaces, strip trailing "-<Bank>" and "(vpa)"; keep original case for display.

CREDIT   \b(credited|received|credit\s+alert)\b   (NOT plain "credit": "credit card", "credit limit")
DEBIT    \b(debited|sent|paid|spent|withdrawn|transferred|deducted|purchase[d]?|charged|emi)\b
```

Ordering of checks in `BankSmsParser.parse()` (return `null` at the first reject):

1. **Hard-reject kinds** by keyword: OTP `\botp\b|one\s*time\s*password|do not share`; collect/request `requested|request(ed)?\s+(rs|inr|₹)|collect request|approve only|tap to pay|decline`; failed/reversed/refund `fail(ed)?|declined|revers(al|ed)|refund|unsuccessful|will be credited back`; promo `apply now|pre-approved|offer|loan up to|http|www\.|t&c|-P$ suffix on header`; balance-only `\bbal\b|balance` with no credit keyword.
2. **Direction**: if a DEBIT verb occurs *before* the first CREDIT verb (Union "debited ... and credited to beneficiary"), or a DEBIT verb is present and no CREDIT verb, reject. Card-bill credits (`towards your ... credit card`) reject.
3. **Amount** required; **UTR** optional (Canara/Paytm PB) → set `utr=null`, and the `Reconciler` should treat amount+time as `LikelyMatch` at best.
4. **Sender trust** (signal, not gate): `senderTrusted = header matches ^[A-Z]{2}-([A-Z0-9]{6})(-[STPG])?$ && group1 ∈ known headers` or, for notifications, `packageName ∈ trusted UPI/bank packages ∪ debug set {com.android.shell}`. A 10-digit / `+91` sender or a header like `SBI-ALERT`/`HDFC-PYMT` is `senderTrusted=false`; still store the row, but the UI/TTS should say "unverified sender" and never let it alone satisfy a Mode 2 `Match`.
5. **Dedupe**: the same credit arrives via SMS *and* the UPI app notification *and* (on the emulator) the Messages app's own notification of the injected SMS. Key on `utr` (or `amount+±2 min` when `utr` is null) within 24 h.

## 3. Android constraints (Android 13–16, verified with sources)

**SMS permissions.** `RECEIVE_SMS`/`READ_SMS` are dangerous runtime permissions in the SMS group and are *hard-restricted*: they are grantable only if the installer allow-listed them; "if this method [`setWhitelistedRestrictedPermissions`] is not used all permissions will be whitelisted" ([AOSP Permissions.md](https://android.googlesource.com/platform/frameworks/base/+/master/core/java/android/permission/Permissions.md)). `adb install`/`pm install` allow-list everything unless `--restrict-permissions` is passed ([PackageManagerShellCommand](https://github.com/aosp-mirror/platform_frameworks_base/blob/master/services/core/java/com/android/server/pm/PackageManagerShellCommand.java)). From Android 15 the Restricted-Settings / Enhanced Confirmation Mode gate was extended from accessibility + notification-listener to the **SMS runtime-permission group**, the SMS/dialer roles, overlay and usage access ([Android Authority](https://www.androidauthority.com/android-15-restricted-settings-sideloading-3481098/), [textbee guide](https://textbee.dev/blog/android-15-send-sms-permission-guide)): on a sideloaded APK the SMS toggle is greyed until the user does **Settings → Apps → CrossCheck → ⋮ → Allow restricted settings** (device lock/biometric prompt), then **Permissions → SMS → Allow**. Sideloaded = installed by a non-session installer (browser, file manager, WhatsApp) — the installer records `PACKAGE_SOURCE_LOCAL_FILE (3)` or `PACKAGE_SOURCE_DOWNLOADED_FILE (4)` and the framework sets app-op `ACCESS_RESTRICTED_SETTINGS = MODE_ERRORED` ([PackageInstaller constants](https://github.com/aosp-mirror/platform_frameworks_base/blob/master/core/java/android/content/pm/PackageInstaller.java), [Kaspersky on 13/14](https://www.kaspersky.com/blog/android-restricted-settings/49991/)). **`adb install` is exempt** — **[emu-verified]** a third-party app installed via adb shows `installerPackageName=null packageSource=1` (= `PACKAGE_SOURCE_OTHER`) and `appops get … ACCESS_RESTRICTED_SETTINGS` → `Default mode: default`. So on the iQOO loaner: install with `adb install`, not by copying the APK. Looking ahead: Android 17 withholds `SMS_RECEIVED_ACTION` for 3 h for apps targeting API 37+ unless they hold an exempt role ([Android 17 behavior changes](https://developer.android.com/about/versions/17/behavior-changes-17)); irrelevant at targetSdk 35 but the SMS path is sunset-bound.

**NotificationListenerService and Restricted Settings.** Since Android 13 notification access for a sideloaded app is blocked with "For your security, this setting is currently unavailable" ([XDA](https://www.xda-developers.com/android-13-restricted-setting-notification-listener/)). Exact unblock steps ([Google Help](https://support.google.com/android/answer/12623953), [Kvaesitso docs](https://kvaesitso.mm20.de/docs/user-guide/troubleshooting/restricted-settings.html)): (1) open Settings → Notifications → Device & app notifications (or the `ACTION_NOTIFICATION_LISTENER_SETTINGS` intent CrossCheck fires) and tap CrossCheck → dialog appears → OK; (2) Settings → Apps → CrossCheck → ⋮ (top-right) → **Allow restricted settings** → authenticate; (3) go back to notification access and enable. The ⋮ entry only appears *after* step 1. Android 14 kept the same session-based rule; Android 15 added the ECM system allow-list on top ([Android Police](https://www.androidpolice.com/android-15-enhanced-confirmation-mode-sideloading/)). adb bypasses: `adb shell appops set com.crosscheck.app ACCESS_RESTRICTED_SETTINGS allow` ([F-Droid #2680](https://gitlab.com/fdroid/fdroidclient/-/work_items/2680); **[emu-verified]** the op exists and is settable on API 36) makes the Settings toggle usable; and `adb shell cmd notification allow_listener com.crosscheck.app/.signal.NotificationListenerSource` grants access outright — it calls `NotificationManagerService.setNotificationListenerAccessGrantedForUser()` directly and never touches the Settings-UI gate ([NotificationShellCmd.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/notification/NotificationShellCmd.java)). **[emu-verified]** it prints nothing and silently does *not* persist for a component that is not installed yet, so run it after `adb install` and confirm with `adb shell settings get secure enabled_notification_listeners`. Android 15+: untrusted listeners receive **redacted** content for notifications where an OTP is detected ([Android 15 changes](https://developer.android.com/about/versions/15/behavior-changes-all)); credit alerts are not OTPs, but if a 12-digit UTR ever trips the heuristic, `adb shell cmd notification redact_otp_from_untrusted_listeners false` exists on API 36 for testing. Read `EXTRA_BIG_TEXT` first, then `EXTRA_TEXT`, plus `EXTRA_TITLE`.

**POST_NOTIFICATIONS.** Runtime permission since API 33; if denied the app cannot post, and a foreground-service notification is hidden from the shade (visible only in Task Manager) but the service still runs ([notification permission](https://developer.android.com/develop/ui/views/notifications/notification-permission)). Request it once from the Log screen; not needed for the listener or receiver to work.

**Background execution / foreground service (14–16).** A manifest-declared `SMS_RECEIVED` receiver keeps working on 14–16 (manifest broadcasts are not queued; the app is taken out of cached state for delivery — [Android 14 changes](https://developer.android.com/about/versions/14/behavior-changes-all)). **[emu-verified]** telephony delivers the broadcast with a 20 s temp-allowlist: logcat shows `tempAllowListReason: android.provider.Telephony.SMS_RECEIVED … reasonCode:EVENT_SMS,duration:20000`, and the receiving app started a foreground service from the background as "Allowed". The documented exemption list does not name SMS explicitly ([FGS background-start restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)), so do not rely on more than that window. Recommended design: in `onReceive` call `goAsync()` (≤10 s) to parse + insert the Room row, then `startForegroundService` of a **`shortService`**-type FGS (no extra permission, ~3 min budget, implement `onTimeout`) that owns the `TextToSpeech` instance and speaks — every FGS on 14+ must declare `android:foregroundServiceType` plus `FOREGROUND_SERVICE` (+ `FOREGROUND_SERVICE_<TYPE>`) ([FGS types](https://developer.android.com/develop/background-work/services/fgs/service-types)). Do **not** use `dataSync` (6 h/24 h budget and `ForegroundServiceStartNotAllowedException` on 15+ — [FGS timeouts](https://developer.android.com/develop/background-work/services/fgs/timeout)); `specialUse` needs `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` and a Play declaration. The notification-listener path is simpler: the service is bound by the system, so speak from `onNotificationPosted` (on a coroutine) without any FGS. Android 15 cancels pending intents on force-stop and redelivers `BOOT_COMPLETED` when the user relaunches; `dataSync`/`mediaPlayback` FGS cannot be started from `BOOT_COMPLETED` on 15+ ([Android 15 FGS types](https://developer.android.com/about/versions/15/changes/foreground-service-types)).

**Google Play SMS/Call-Log policy.** `READ_SMS`/`RECEIVE_SMS` may only be requested by the default SMS/Phone/Assistant handler or under a case-by-case exception; the exception list does include "SMS-based financial transactions (e.g. UPI)" and "SMS-based money management", but exceptions require a declaration form, are reviewed manually and must be a small fraction of installs ([Play policy](https://support.google.com/googleplay/android-developer/answer/10208820), [2027 preview](https://support.google.com/googleplay/android-developer/answer/17225965)). `NotificationListenerService` is outside that policy (it needs only user consent in Settings), so it is the Play-safe production path; keep `RECEIVE_SMS` for the emulator gate and as an opt-in on sideloaded builds.

## 5. Tamil TTS on the Google Play emulator image (**[emu-verified]**)

- Engine: `adb shell settings get secure tts_default_synth` → `com.google.android.tts` ("Speech Recognition and Synthesis from Google", version `googletts.google-speech-apk_20260803.02`). Tamil (India) is a supported language, but "users must install voice data for each language" ([Wikipedia: Speech Recognition & Synthesis](https://en.wikipedia.org/wiki/Speech_Recognition_%26_Synthesis)); the image ships **only `English (United States)`** offline.
- One-time download (~9.9 MB, took ~10 s over the emulator's Wi-Fi — the *engine* needs network, CrossCheck does not): `adb shell am start -n com.google.android.tts/com.google.android.apps.speech.tts.googletts.local.voicepack.ui.VoiceDataInstallActivity` → scroll to **Tamil (India)** under "Available languages" → tap → **Download (~9.9 MB)**. logcat confirms `VoiceDataDownloader: Download ta-in Success true`; afterwards "Your languages" lists `Tamil (India)` with "Voice I" and "Voice II". Equivalent UI route: `adb shell am start -a com.android.settings.TTS_SETTINGS` → Preferred engine ⚙ → Install voice data ([Google accessibility help](https://support.google.com/accessibility/android/answer/6006983)). The pack lives in the AVD's data partition, so **snapshot the AVD** after downloading (a wipe/cold-boot with `-wipe-data` loses it). Repeat once on the iQOO loaner.
- Programmatic check for `Speaker`: after `onInit`, `tts.isLanguageAvailable(Locale("ta","IN"))` returns `LANG_COUNTRY_AVAILABLE` (0/1/2 ≥ 0) once the pack is installed and `LANG_MISSING_DATA (-1)` before; `tts.voices.filter { it.locale.language == "ta" && !it.isNetworkConnectionRequired }` should be non-empty. If missing, fire `Intent(TextToSpeech.Engine.ACTION_INSTALL_TTS_DATA)` from Settings and speak the fallback `en-IN` string. There is no shell-level `isLanguageAvailable`; the closest is the UI dump above (`adb shell uiautomator dump` and grep "Tamil (India)" under "Your languages").
