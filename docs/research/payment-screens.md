# Mode 2 research: GPay (India) and PhonePe payment screens

Scope: what the Android **Google Pay (India)** and **PhonePe** "payment successful" and "transaction details" screens actually contain in 2025-26, what fake generators produce, how to extract `{amount, upi_id, utr, timestamp}` from a **photo of another phone's screen**, an 8-image fixture plan, and whether exact-UTR matching is sound. Written 2026-09-06 against `docs/SPEC.md` §1 Mode 2 and §4 (money as `Long` paise, UTR normalised to digits, no forensics).

Legend: **[V]** verified against a cited source · **[I]** inferred from widely circulated screenshots / general knowledge, not confirmed by a fetched source — re-check on the loaner device at the event. No branded assets were downloaded or copied; screenshots are described only.

Key findings up front:

1. The **12-digit UTR/RRN is the only cross-app, cross-bank identifier.** GPay calls it "UPI transaction ID", PhonePe calls it "UTR", the payee's bank SMS calls it "UPI Ref No". One number per transaction, generated by NPCI, shared by both banks. [V] Exact matching on it is reliable; all other IDs (PhonePe `T…`, Google `CICAg…`) are app-internal and never appear on the payee side.
2. **Fake generators produce format-valid 12-digit UTRs** (user-typed or random). [V] Format checks are worthless; only reconciliation against our `payments` table catches them, which is exactly the SPEC design.
3. **The payer's own UPI ID is usually *not* on the payer's screen.** GPay shows "From: <Name> (Bank XX1234)", PhonePe shows "Debited from <Bank> XX1234". The `@handle` visible is normally the **payee's** (i.e. the seller's own). The `flagged_vpas` repeat-offender key therefore needs a fallback (payer display name, bank-mask) - see §3a and §6.
4. Pending screens exist on both apps and are used in a known scam ("cancel at the last millisecond, screenshot the in-progress screen"). [V] Extractor must emit `status: "pending"` and the reconciler must never map that to `Match`.

## 2. What fake generators and spoof APKs produce

Sources (all 2026): Razorpay "Fake Payment Screenshot Scam 2026" (2026-02-11); ScamDekho "Fake UPI Payment Apps in India" (2026-04-16) and "Fake PhonePe Transaction Scam" (2026-06-07); Pine Labs "Fake payment screenshot fraud - 2026 guide" (2026-05-21); ScamScan "Fake Payment Screenshot Examples" (2026-05-31); Cashfree (mid-2026); PhonePe Business "Fake UPI Payment Scams" (Aug 2026); generator sites fakereviewgenerator.com/payment/phonepay and invoicepracticelab.com (GPay + PhonePe "receipt generators"); vlivetricks.com (tool withdrawn - "People is Using for Illegal Activities").

**Three production methods** [V, Razorpay/Cashfree]: (1) edited real screenshots; (2) browser generators - type name, amount, UPI ID, IDs, date; (3) spoof APKs (distributed on Telegram/WhatsApp) that "imitate Google Pay or PhonePe interfaces almost perfectly ... copy the colors, layout, fonts, and even the transaction sounds" and show a live "success" animation on the customer's own phone - i.e. exactly the thing our camera will be pointed at. (4) A fourth trick needs no tooling: start a real payment and cancel/screenshot the **pending** screen [V, Cashfree].

**Fields they let you set** [V, fakereviewgenerator + invoicepracticelab]: status (Success/Pending/Failed), amount (2 decimals), sender name, receiver name, receiver VPA, transaction ID, date & time, note, sender bank + masked account, **UTR (free-text numeric)**; export PNG/JPG/PDF with optional fake EXIF. The GPay generator renders `Transaction ID CICAgKD…`, `UTR 123456789012`, an 18-digit "UPI Reference ID", VPAs, `SBI ••••1234`, `₹1,500.00`, `24 Mar 2025, 3:45 PM`.

**Do they generate plausible 12-digit UTRs? Yes.** ScamDekho (2026-04-16): fake apps produce "matching 12-digit numeric strings that look correct but won't appear in any bank's records"; GPay clones are sloppier ("all-numeric IDs or random alphanumeric strings"). The PhonePe generator uses a wrong `TXN`-prefixed transaction ID instead of `T`+22 digits [V] - a tell we deliberately ignore. Note ScamDekho also (incorrectly) states "Real PhonePe transaction IDs are exactly 12 digits" - they conflate UTR with the T-id; do not copy that claim into prompts.

**Tells the industry lists that are irrelevant to us** (SPEC §1: no forensics): blurry/stretched logos, font/colour drift, cropped top bar, missing IDs, generic UPI handles, mismatched timestamps, EXIF. The one thing every source agrees on is our design: "match UTR or transaction ID, amount, and timestamp" against your own records [V, Pine Labs]; "even a single-digit mismatch ... confirms fraud" [V, Pine Labs].

Implication for the extractor: a spoof screen is **pixel-faithful**, so the VLM/OCR will read it cleanly; the only defence is that its UTR is not in `payments`. Also expect adversarial inputs: a real screenshot of a *different* payment (right UTR, wrong amount edited) - which is why `Match` requires amount **and** UTR.

## 3. Extraction guidance

### 3a. VLM prompt (one pass, image -> strict JSON)

System:

```
You read photographs of a phone screen showing an Indian UPI payment app. The photo is taken with another phone, so expect glare, moiré, perspective tilt, partial cropping and bright-on-dark text. Two layouts occur:
- Google Pay (India): green tick, large "₹" amount, "Paid to <name>" or "To <name>", a status word ("Completed", "In progress", "Failed"), and in the details block the labels "UPI transaction ID" (12 digits), "To:", "From: <name> (<Bank> XX1234)", "Google transaction ID" (starts "CICAg").
- PhonePe: "Payment Successful" / "Transaction Successful" (or "Pending"/"Failed"), large "₹" amount, "Paid to <name>", a date line like "06 Sep 2026, 12:41 pm", and a details block with "Transaction ID" (T followed by 22 digits), "UTR" (12 digits), "Debited from <Bank> XXXXXX1234".
Return ONLY a JSON object, no prose, no code fence:
{"amount_paise": int|null, "upi_id": string|null, "utr": string|null, "timestamp": string|null, "app": "gpay"|"phonepe"|"unknown", "status": "success"|"pending"|"failed"|"unknown"}
Rules:
1. amount_paise = the large headline rupee amount × 100 as an integer (₹1,250.50 -> 125050). Ignore small amounts in "Debited from" rows unless no headline amount is legible.
2. utr = the 12-digit number labelled "UPI transaction ID", "UTR", "UPI Ref No", "Bank reference ID" or "RRN". Digits only. Never put a "T…" PhonePe Transaction ID, a "CICAg…" Google transaction ID, a phone number or an account number here. If no 12-digit UTR is fully legible, use null.
3. upi_id = a UPI handle of the form name@bank visible on screen (prefer the one under "To"/"Paid to"). null if none.
4. timestamp = the date/time shown, copied verbatim (e.g. "6 Sept 2026, 12:41 pm"). null if not fully legible.
5. status: "success" only if a completed/successful indicator is visible; "pending" for processing/in progress/pending; "failed" for failed/declined/reversed; else "unknown".
6. If a value is partially hidden by glare, cut off by the frame, or you would have to guess a digit, return null for that field. Never invent digits.
```

User (per frame): `Extract the payment fields from this photo.` followed by the image. Keep temperature 0; enforce the schema with a tolerant JSON extractor (first `{`..last `}`), and treat any non-JSON or a `utr` that is not `^\d{12}$` after normalisation as "VLM failed -> OCR fallback" (SPEC §1).

Recommended schema extension (does not break the required shape): add `"payer_name": string|null` (from "From:"/"Debited from" context or the sender line) so `flagged_vpas` can key on something when no payer VPA is on screen; and `"other_ids": [string]` for the T-/CICAg- IDs for the receipt row.

### 3b. OCR fallback (ML Kit lines -> `ClaimFieldParser`)

Work on ML Kit `Text.TextBlock`/`Line` objects with bounding boxes; normalise `O->0`, `l/I->1`, `S->5`, `B->8` **only inside digit runs**, strip spaces inside digit runs, and treat `₹`, `Rs`, `Rs.`, `INR`, and common OCR misreads of ₹ (`?`, `Z`, `₹` read as `3` or `र`) as the currency marker.

```
AMOUNT   (?:₹|Rs\.?|INR|\?)\s?(\d{1,3}(?:,\d{2,3})*|\d+)(?:\.(\d{1,2}))?
         pick the candidate whose bounding-box height is largest and whose top edge is in the top ~45% of the frame;
         paise = rupees*100 + (decimals padded to 2). Indian grouping (1,50,000) -> just strip commas.
         Reject candidates adjacent to "Debited from"/"From" unless nothing else is found.
UTR      (?<!\d)(\d{12})(?!\d)
         rank: +3 if the same line or the line above matches /UPI\s*transaction\s*ID|UTR|UPI\s*Ref|RRN|Bank\s*ref/i;
               -3 if it is a substring of a longer digit run (T-id, account number, 18-digit PG ref);
               -2 if it starts with 91 followed by [6-9] (looks like +91 mobile);
               +1 if first digit is the current year digit (6 in 2026) and digits 2-4 <= 366 (soft prior only).
PHONEPE  \bT\d{20,22}\b      -> app = phonepe; store in other_ids; utr stays null unless a separate 12-digit run scores >= 0
GPAY     \bCICAg[A-Za-z0-9_-]{6,}\b -> app = gpay; store in other_ids
UPI_ID   \b[a-z0-9._-]{2,}@[a-z]{2,}\b   (lower-case the line first; ML Kit often reads @ as "a" or "©" - accept [@©] then normalise)
APP      gpay if /Google\s*transaction\s*ID|UPI\s*transaction\s*ID|Google\s*Pay|G\s*Pay/i;
         phonepe if /PhonePe|\bUTR\b|Debited\s*from|Transaction\s*ID\s*:?\s*T\d/i;  if both, prefer the one with more hits.
STATUS   success: /Completed|Successful|Success|Payment\s*Successful|Transaction\s*Successful|Paid\s*to|Sent\s*to/i
         pending: /Processing|Pending|In\s*progress|Initiated/i
         failed : /Failed|Declined|Unsuccessful|Reversed|Refund/i
         precedence: failed > pending > success (a pending screen may still say "Paying <name>"; a failed one may still say "Paid to")
TIME     (\d{1,2})\s+(Jan|Feb|Mar|Apr|May|Jun|Jul|Aug|Sep|Sept|Oct|Nov|Dec)[a-z]*\.?,?\s+(\d{4}),?\s*(?:at\s+)?(\d{1,2}):(\d{2})\s*([AaPp]\.?[Mm]\.?)?
         | (Jan|...|Dec)[a-z]*\s+(\d{1,2}),\s*(\d{4})\s+at\s+(\d{1,2}):(\d{2})\s*([AP]M)      # "December 8, 2020 at 7:25 PM" (GPay export style)
         | (Today|Yesterday),?\s+(\d{1,2}):(\d{2})\s*([AaPp][Mm])?                                 # history-row style
         | (\d{2})[-/](\d{2})[-/](\d{2,4})\s+(\d{1,2}):(\d{2})                                    # bank-SMS style, just in case
         Parse in Asia/Kolkata, 12h if am/pm present else 24h, -> epoch millis UTC. "Sept" must map to September.
```

Heuristics: run the amount regex on the top half first; run the UTR regex on the bottom two-thirds first; if the frame contains only the hero region (no details block), return `utr: null` rather than a low-confidence number - the SPEC's `LikelyMatch` on amount+timestamp still gives the seller a useful answer. If `status == pending`, still return amount/timestamp; the reconciler should answer "NO MATCH - payment still pending on the customer's side" (SPEC §1 lists no pending verdict; recommend adding this reason string).

### 3c. Photographing a screen - artefacts and capture tips

Physics [V, arXiv 2602.01559, 2026-02-02]: **flicker banding** = rolling-shutter rows sampling different phases of the panel's **PWM** dimming (worst on OLED at low brightness and with short exposures); **moiré** = aliasing between the display pixel grid and the sensor grid (worst when the screen fills the frame at a magnification where pitch ≈ sensor pitch, and on LCDs; OLED pentile is somewhat softer [V, removemoire.com]).

Practical tips (seller-side, spoken by the app if needed):
- Ask the customer to **raise brightness to max** - most OLED panels stop PWM dimming (or use DC dimming) above ~50-80 % and the text-to-background contrast improves; also lets our camera use a shorter ISO.
- Hold 20-30 cm away so the screen fills ~60-70 % of the frame, **tilt ~10°** off-axis (kills specular glare from ceiling lights and shifts moiré), **torch off**.
- **Tap-to-focus on the amount**, wait for AF to settle (~300 ms), then capture; auto-capture only when ML Kit finds >= 1 `₹` line and >= 1 12-digit run in two consecutive frames.
- Prefer landscape-free, portrait framing so the details block is not cut off.

CameraX settings (all in `androidx.camera.core`, doc-verified [V, developer.android.com/media/camera/camerax/configuration]):
- `cameraControl.startFocusAndMetering(FocusMeteringAction.Builder(point, FLAG_AF or FLAG_AE).setAutoCancelDuration(3, SECONDS).build())` with `point = previewView.meteringPointFactory.createPoint(x, y)` on the tapped/centre region.
- `cameraControl.setExposureCompensationIndex(i)` with `i ≈ -1 EV / exposureState.exposureCompensationStep` - a bright screen on a dark background blows out white text otherwise; check `cameraInfo.exposureState.isExposureCompensationSupported`.
- After metering settles, lock AE via `Camera2Interop.Extender(builder).setCaptureRequestOption(CaptureRequest.CONTROL_AE_LOCK, true)`; optionally cap exposure to >= 1/60 s (`CONTROL_AE_MODE_OFF` + `SENSOR_EXPOSURE_TIME`) to average full PWM cycles - device-specific, keep behind a settings toggle.
- `cameraControl.enableTorch(false)`; `ImageCapture.CAPTURE_MODE_MAXIMIZE_QUALITY`; analysis resolution >= 1080p with `ResolutionSelector`; feed ML Kit a full-resolution `ImageCapture` frame, not the 640×480 analysis stream (ML Kit wants characters >= ~16 px tall [I]).
- Note that all of these **reset when the camera is unbound**; re-apply in `onResume`.

## 5. Timestamp / UTR realities

- **Length:** UPI RRN/UTR is exactly 12 numeric digits [V: PhonePe Business (Jun 2026), xflowpay (2026-08-20), Paytm blog (2026), Hero FinCorp (2026-01-28), PayU (2026-02-26)]. Structure `Y DDD NNNNNNNN` (ISO 8583 convention) [V, Hero FinCorp; corroborated by Bitbns's "2021 IDs start with 1" and the SPEC's `4261…` sample].
- **Identical on payer and payee side? Yes.** It is generated once by NPCI's switch per transaction ("the only one banks use to track the actual movement of money" [V, Paytm]), quoted by both banks in reconciliation/dispute flows, and is the number the NPCI complaint portal routes on [V, Zwitch; xflowpay]. No fetched source states the contrary. Confidence: high, but the primary NPCI page did not render - mark as "verified by convergence of secondary sources".
- **Does the payee's bank SMS carry the same UTR?** Yes: bank SMS shows `UPI Ref No 620345230917` [V, xflowpay] and statement narrations carry the 12-digit reference in the `UPI/…/<ref>/…` field [V, mybankstatementanalysis 2026], which is why the SPEC's Mode 1 SMS template (`UPI Ref No 426112345678`) lines up with the payer's screen. Caveat: some bank narrations truncate/relabel (Google's help even says "the UPI transaction ID is usually the first 9 digits after the slash" for some statement formats [V, Help 9739577]) - hence the SPEC's ≥ 8-digit prefix/suffix partial match is the right safety net.
- **Can GPay show a different "UPI transaction ID" than the bank's RRN?** For ordinary P2P/P2M UPI payments the 12-digit "UPI transaction ID" *is* the RRN [V, scribd example + Bitbns + eximpe]. Differences arise only when (a) the screen shows the **Google transaction ID** (`CICAg…`) - never matches anything on our side; (b) a merchant/PG flow shows a long alphanumeric PSP reference alongside; (c) a failed-then-reversed payment gets a new RRN for the reversal [V, Help 16920039]. None of these break exact matching if we only ever compare 12-digit runs.
- **Timestamps:** the payer's screen shows the app's local completion time; the bank SMS carries the bank's posting time; they typically agree within seconds to a couple of minutes [I]. The SPEC's 10-minute tolerance is generous enough; do not tighten below ~3 min.

**Decision:** exact 12-digit UTR + amount matching is reliable and is the correct primary key for `Match`. Fake screens cannot be detected by format, only by absence from `payments`. The payer's VPA is usually absent from the screen, so key `flagged_vpas` on the best available of `payer VPA -> payer name -> bank-mask`, and say so in the receipt.
